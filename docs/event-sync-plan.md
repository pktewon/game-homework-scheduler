# 데이터 처리와 이벤트 자동 업데이트 설계

김태준 · 2026626007 · 게임 숙제 스케줄러

일정 자동 수신과 개인 완료 수동 체크를 확정했다. 앱의 검수된 JSON 수신·Room 병합을 목표로 하고, 원문 수집기는 게임별로 검증한다. 실제 이용 환경은 명조·엔필 Asia, 소전2 HAOPLAY 한국판이다. [공지 수집 상세 설계](notice-ingestion-design.md)에 게임별 경로·분해·식별자·저장 보완안을 정리했다.

이 문서의 자동 업데이트는 공통 일정의 기간·제목·출처 갱신이다. 기말 버전에서 개인의 참여·보상 수령은 직접 체크하며, 게임 실행이나 앱 복귀로 완료 처리하지 않는다. 엔드필드 공식 도구의 일일·주간 정보와 다른 두 게임의 연동 범위는 [세 게임 연동 검토](integration-decision.md)에서 구분했다.

## 앱 내부 데이터 처리

![Room 데이터 처리 흐름도](design/data-flow.png)

| 구성 요소 | 맡을 역할 |
| --- | --- |
| Entity | 테이블, PK·FK와 인덱스 정의 |
| DAO | CRUD, 홈 목록 조회, 체크 변경, 회차별 완료 기록 조회·저장 |
| AppDatabase | Entity·DAO 등록, 버전과 마이그레이션 관리 |
| Repository | 입력 검사, 회차 계산, 연결 검사, 트랜잭션과 일정 병합 |
| ViewModel | 화면 상태와 조회 결과 관리, 앱 복귀 시 시간 기준 갱신 |
| Fragment | 입력과 클릭 전달, RecyclerView와 상세 화면 표시 |

Room을 앱 화면의 로컬 데이터 기준으로 사용한다. 이벤트 저장과 참여 항목 저장은 함께 처리한다. 숙제 완료 체크는 현재 회차를 계산한 뒤 기록을 추가하고, 메모 저장은 연결된 게임·이벤트가 일치하는지 확인한다.

## 단계별 구현 범위

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 필수 | 사용자가 공식 공지를 보고 일정 수동 등록 | 인터넷 없이도 등록·조회·수정·체크와 기록 보존 가능 |
| 앱 목표 | 검수한 JSON을 받아 Room에 병합 | 같은 JSON을 반복 적용해도 이벤트가 중복되지 않고 개인 기록 보존 |
| 확장 2 | 대표 게임 한 개의 공식 공지 추출 실험 | 제목·서버·시작·종료·출처를 원문과 대조해 검증 |
| 후속 | 여러 게임 수집 경로와 AI 추출 보조 확대 | 수집 유지보수와 검수 체계를 마련한 뒤 범위 결정 |

![공식 공지 수집부터 Room 병합까지의 흐름](design/sync-flow.png)

공지 수집과 AI 추출을 앱 내부에서 모두 처리하는 방식은 1인 기말 필수 범위에서 제외한다. 검수한 JSON 배포 경로 역시 확장 구현 시 준비해야 하며, 현재 운영 중인 서버는 없다.

## 일정 데이터와 식별 기준

외부 일정에는 게임, 서버·지역, 고정 `sourceKey`, 제목, 시작·종료 시각, 원문 주소, 갱신 시각이 필요하다. 참여와 보상 교환의 기간이 다르면 별도 `sourceKey`를 부여하고 같은 `groupKey`로 연결한다.

시각은 명확한 시간대가 포함된 값으로 검수한 뒤 UTC로 변환한다. 원문에 종료 일시가 없으면 NULL과 확인 필요 상태로 유지한다. 제목이나 날짜가 바뀌어도 같은 일정은 같은 `sourceKey`를 사용해야 한다.

## 병합과 오류 처리 규칙

1. 게임·서버·키·필수 값과 기간을 검사한다. 종료가 시작보다 이른 데이터는 반영하지 않는다.
2. `(gameId, sourceKey)`로 기존 이벤트를 찾고, 있으면 동일한 `eventId`를 유지한다.
3. 검수된 AUTO 일정의 제목·기간·출처 등 메타데이터를 반영한다. 직접 수정한 MANUAL 일정이나 불명확한 변경은 확인 대기로 둔다.
4. 참여 체크·보상 체크·숙제 완료 기록·메모는 기존 값을 보존한다. 새 항목이 필요하면 사용자 완료 상태와 구분해 추가 검토한다.
5. 원문에서 누락된 이벤트를 자동 삭제하지 않는다. 수집 실패 시 기존 데이터를 유지하고 실패 상태를 표시한다.
6. 성공한 경우에만 `lastSuccessAt`을 갱신한다. 마지막 성공 시각을 보여 정보의 최신 여부를 확인할 수 있게 한다.

## 갱신 시점과 검증

앱 실행 시 마지막 갱신이 오래되었으면 새 정보를 확인하고, 수동 새로고침을 제공할 예정이다. 배경 갱신을 추가할 때는 WorkManager를 사용한다. 운영체제와 배터리·네트워크 조건에 따라 실행이 지연될 수 있어 마감 시각의 실시간 반영을 보장하지 않는다. 이 제약은 [Android Developers WorkManager 문서](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)를 기준으로 검토했다.

중복 적용, 날짜 변경, 네트워크 실패, 잘못된 기간, 서버 시간대 변환, 수동 수정 보호, 보상 미수령 유지 등을 확인한다. AI를 이용해 날짜 후보를 추출하더라도 공식 원문과 시간대를 검수한 뒤 적용한다.
